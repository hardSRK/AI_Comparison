Executive Summary
What the board needs to know in under 3 minutes
🏛️
Board Recommendation

Build SRK's company chatbot on the Claude API (Anthropic) using Claude Sonnet 4.6 as the primary model, deployed through the existing Azure infrastructure. This is not simply the cheaper option — it is the only option that gives SRK legal and operational control over how AI is used within the organisation.

💰 Cost
API at typical use: $800–1,600/month for 100 active users. 100 individual Pro licences: $2,000/month fixed, with no central control and daily message caps.
⚖️ Governance
Individual licences give SRK zero visibility into what employees ask, what data they share, or what the AI produces. A single employee could paste confidential client data with no trace.
🔒 Control
The API model allows SRK to enforce rules, log every conversation, integrate with Azure systems, and restrict scope — all configured by IT. Employees cannot bypass the system prompt.
📋 Compliance
South Africa's POPIA requires lawful processing of personal data. The API model — with SRK owning the data layer — is far more defensible than individual accounts on US-hosted platforms.
🚀 Implementation
8-week build to full rollout. Proof of concept achievable in 4 weeks. Initial build requires 2 developers. Ongoing management: 20–30% of one person's time after launch.
🌍 Geopolitical
Anthropic faces a Pentagon dispute that may affect US government access, but commercial API access is unaffected. MCP open standard provides exit capability if needed.

Why individual licences are not a solution

The temptation to simply issue 100 Claude Pro or ChatGPT Plus licences is understandable — it requires no development. But this approach is ungovernable by design:

With the API model, every conversation is logged in SRK's own database and can be reviewed immediately.

💡
Why this architecture gives SRK control that individual licences cannot

With individual licences, employees send messages directly to Claude.ai or ChatGPT — there is no Layer 2. No system prompt. No input filter. No audit log. No role-based access. No spend cap. The entire governance capability comes from Layer 2, and Layer 2 only exists in the API model.

Claude has no memory between sessions. Every API call must contain the complete context — assembled by the SRK application layer. Here is exactly what gets sent and why.

1
📋 System Prompt Cached — 90% cheaper after first call
The system prompt is SRK's master instruction document. It defines scope, restrictions, tone, and edge case handling. Sent with every message — but after the first call Anthropic caches it and charges only 10% of the normal input rate. This single optimisation saves over 90% of system prompt cost.
// Simplified SRK system prompt structure { "role": "system", "content": "You are SRK Consulting's internal AI assistant. SCOPE: Assist with SRK projects, company policies, and technical work in our domains (geotechnical, environmental, mining). General professional tasks also in scope. RESTRICTIONS: - Never discuss competitor strategies or pricing - Never provide legal or financial investment advice - Never share one client's information with another client - Always caveat uncertainty in technical judgements TONE: Professional, precise, direct. This is a business tool. EMPLOYEE CONTEXT: {ROLE_INJECTION_PLACEHOLDER}", "cache_control": { "type": "ephemeral" } ← enables 90% discount }
💰 100 users × 15 msgs/day × 1,000-token prompt = 1.5M tokens/day. Without caching: $4.50/day = $135/month. With caching: $13.50/month. Enable on day one.
2
🎭 Role Injection
After Azure Entra ID authentication, the application layer fetches the employee's profile and appends it to the context. This allows the same system prompt to behave differently for different roles — no separate prompts per department.
// Injected per request — replaces {ROLE_INJECTION_PLACEHOLDER} EMPLOYEE_ROLE_CONTEXT = { "employee_id": "E4421", "name": "Dylan", "role": "Senior Data Analyst", "department": "Data Services", "skills_access": ["sharepoint", "library", "project_lookup", "code_gen"] } // Junior analyst: ["sharepoint", "library"] only // Director: adds ["project_financials", "generate_report"]
3
🧠 Conversation History
Claude has no memory between API calls. The context manager retrieves this session's conversation history from Azure SQL and prepends it. As conversations grow long, older turns are automatically summarised to manage the token budget.
// Previous turns retrieved from Azure SQL, included in messages array [ { "role": "user", "content": "Find Cape Town geo reports from 2023" }, { "role": "assistant", "content": "I found 3 reports: CT-GEO-2023-01..." }, { "role": "user", "content": "Summarise the borehole findings from the second one" } // ← Current message appended here by the assembler ]
4
🔌 Skill Execution (if needed)
If the query requires SRK data, the application layer calls the relevant skill before the API call. The result is injected into the context. Claude never directly accesses any SRK system — it only sees what the skill returns.
// App layer detects intent → calls skill BEFORE the API call skill_result = search_library(query="Cape Town borehole 2023") { "role": "tool_result", "content": "[{title:'CT-GEO-2023-01: Cape Town CBD Borehole Investigation', author:'J.Smith', date:'2023-04-12', link:'https://...'}]" } // Claude uses this real data — it never had direct library access
5
📦 Final Assembled API Call
The API assembler combines everything into one well-formed payload sent to Anthropic. The total token count determines the cost. The system prompt component is cached, making it 90% cheaper.
// Final payload sent to api.anthropic.com/v1/messages { "model": "claude-sonnet-4-6", "max_tokens": 2048, "system": [{ "type": "text", "text": "[SRK system prompt]", "cache_control": { "type": "ephemeral" } }], "messages": [ { "role": "user", "content": "[role injection context]" }, { "role": "assistant", "content": "[history turn 1]" }, { "role": "user", "content": "[history turn 2]" }, { "role": "tool_result", "content": "[skill results if any]" }, { "role": "user", "content": "[current employee message]" } ], "tools": [/* registered MCP skill definitions */] }
System ~1,000+ Role ~100+ History ~1,500+ Skills ~500+ Message ~100= ~3,200 input tokens
💡 At $3/M input tokens with caching: ~3,200 tokens ≈ $0.007/message. Output (~600 tokens) ≈ $0.009. Total ~$0.016/message. At 15 msg/day × 70 users ≈ ~$1,000/month at typical use.
6
↩️ Response Processing & Storage
Claude's response returns to SRK's application layer. The output filter reviews it. The full exchange is logged to Azure SQL. The response is delivered to the employee's chat window.
response = claude_api.call(payload) ← Claude returns text filtered = output_filter.check(response) ← SRK reviews response azure_sql.log({ employee_id:"E4421", timestamp:"2026-04-21T14:32Z", user_message:"[what they asked]", ai_response:"[Claude's answer]", tokens_in:3200, tokens_out:580, cost_usd:0.0182 }) send_to_ui(filtered) ← Employee sees the answer

03
Governance, Brand & Client Data Control
What SRK must control — and how the API model enforces it technically
🚨
The Core Risk of Individual Licences: Zero Governance

With 100 individual AI accounts, SRK is effectively operating 100 unmonitored AI pipelines. Any employee could share a confidential proposal, a client's financial data, or internal HR information with an external platform — and SRK would never know. If this data appeared in a competitor's model, or formed the basis of an AI hallucination in a client report, SRK would have no record and no defence.

What the API model lets SRK control

Control Mechanism How It Works What It Prevents
System Prompt A master instruction set defining scope, tone, and restrictions. Sent with every message. Employees cannot see or modify it. Off-topic use, competitor research, personal tasks, inappropriate content
Role-based access Application layer injects the authenticated employee's role into every API call. Junior analysts get different capabilities than directors. Junior staff accessing sensitive skills or financial data above their clearance
Input filtering Application can scan employee messages before they reach the API and block or flag sensitive patterns (client names, project codes, financial figures). Accidental or deliberate data exfiltration via the chatbot
Output filtering AI responses can be reviewed by the application layer before delivery. Certain content types can be blocked or flagged. AI producing content that doesn't meet SRK's professional standards
Conversation logging Every message, by every employee, is logged to SRK's own Azure SQL database — including timestamps, employee ID, and token cost. Inability to investigate incidents, audit compliance, or monitor usage patterns
Skills scoping Custom skills (SharePoint, project lookup) are written by SRK's team and only expose the data they are explicitly coded to return. Employees using the AI to access data outside their authorised scope
Spend cap Monthly spend cap set in the Anthropic console. Alert triggered at 80% of budget. Automatic cutoff at limit. Runaway costs from unexpected heavy usage

Brand & image protection

SRK's reputation as a professional consulting firm depends on the quality and accuracy of work delivered to clients. With individual AI licences, employees could use AI to draft client reports, proposals, or emails with no oversight — and those outputs might contain AI hallucinations, confidential cross-client data, or content that doesn't meet SRK's standards.

⚠️ Risk: Individual Licences
  • Employee drafts client report with AI — includes hallucinated references
  • Employee pastes Client A's data while working on Client B — cross-contamination
  • SRK has no record of what was generated, no ability to investigate
  • Client discovers AI-generated content that doesn't meet agreed standards
  • Potential lawsuit: SRK cannot demonstrate due diligence
✅ Mitigated: API Model
  • System prompt defines SRK's tone, caveats, and professional standards
  • All conversations logged with employee ID and timestamp
  • Full audit trail available for any investigation within hours
  • Skills scoped so cross-client data contamination is structurally prevented
  • SRK can demonstrate governance and compliance to any client or regulator

Are Azure costs accurate?

Yes, for the scale described. Azure SQL at General Purpose 2 vCores handles thousands of concurrent read/writes comfortably. Storage costs for chat history are minimal — 100 users generating 15 messages/day produces roughly 5–15 MB of text per day, or 1.5–4.5 GB per year. At Azure's standard rate of $0.115/GB/month for SQL storage, this costs approximately $0.20–$0.50/month for the chat history alone — negligible. Blob storage for file uploads scales similarly. The dominant cost is always the API token spend, not storage.

What is a Token?
Plain-language explanation of how AI pricing works — with examples
📖
A token is not a word — it's a chunk of text

AI models don't read words — they read tokens. A token is roughly 3–4 characters of English text. Short common words are one token; longer or unusual words may be two or more. Numbers, spaces, and punctuation each consume tokens. On average, 1,000 tokens ≈ 750 words of English text.

Example: how this sentence is tokenised
SRK Consult ing uses Claude API for geo tech nical work .
↑ Each coloured block = one token Notice: "Consulting" splits into "Consult" + "ing" "geotechnical" splits into 3 tokens Full stop = its own token

How tokens are consumed in a chatbot conversation

What costs more than you might expect

📄 Uploading a large document
A 20-page PDF might be 15,000–25,000 tokens. At $3/million input tokens, that's $0.05–$0.08 per upload. Still cheap — but upload of entire document libraries would add up. Use skills to search and retrieve only relevant sections rather than uploading whole documents.
💬 Very long conversations
Every message includes the full conversation history as context. A 20-message conversation may be 10,000+ input tokens by the end. This is why conversation history management (summarising old turns, truncating) is worth implementing in the application layer for power users.
💰
The #1 cost saver: prompt caching

Your system prompt is sent with every single message. Without caching, 100 users × 15 messages × 1,000-token system prompt = 1.5M tokens of system prompt input per day, costing ~$4.50/day = $135/month just for the system prompt. With prompt caching enabled, that same prompt costs $13.50/month — a saving of over 90%. Enable this on day one.

UI Friendliness & Usability
How simple can we make it? What is the learning curve?
✅
The UI can be as simple as WhatsApp

Because SRK builds the interface, it can be designed specifically for SRK's employees. No menus to configure, no settings to understand, no model to choose. An employee opens the browser, logs in with their normal SRK credentials, types a question, and gets an answer. That is the entire experience for most users.

Recommended UI principles for SRK

🎯 Single-task focus
The chat interface does one thing: answer questions and complete tasks. No settings panel visible to employees. No model selection. No configuration. One text box, one send button.
📜 Conversation history
Left-panel sidebar showing past conversations, searchable by keyword. Click a conversation to resume it. Employees find their previous work instantly — no re-typing context.
📎 File upload
Drag-and-drop a PDF, DOCX, or XLSX into the chat window. The AI reads it and answers questions about it. No file management system — just upload and ask.
💡 Suggested prompts
New users see 4–6 suggested prompts relevant to SRK's work (e.g. "Summarise this report", "Find similar projects", "Draft an email about..."). Removes blank-page anxiety.
🔖 Skill buttons
Quick-access buttons for common skills: [Search SharePoint] [Find Project] [Search Library]. One click to trigger the most-used integrations without typing a prompt.
📊 Feedback button
Thumbs up/down on every response. Feeds into admin dashboard for system prompt refinement. Employees feel heard; IT learns what to improve.

Including Coding Capabilities
How to let employees write, run, and generate code through the chatbot

Coding assistance is included in the Claude API at no additional cost — Claude Sonnet 4.6 is among the top-rated models for code generation, debugging, and explanation. The question is not whether to include it, but how to present it safely to employees of varying technical ability.

Three levels of coding integration

Level 1 — Code generation only (recommended for launch)

Claude writes code in the chat window. Employee copies it and runs it themselves in Excel, Python, or wherever needed.

What it handles: Python scripts, SQL queries, VBA macros, Excel formulas, geotechnical calculations, data cleaning scripts, borehole log processing.

No additional infrastructure — works out of the box

Level 2 — Code + file generation (Phase 2)

A generate_report skill accepts Claude's structured output and produces downloadable .docx, .xlsx, or .pdf files using Python libraries (python-docx, openpyxl).

What it handles: Employee asks "generate a borehole log summary from this data" → downloads a formatted Word document.

1–2 weeks dev per skill

Level 3 — Code execution sandbox (Phase 3)

A sandboxed Python environment (Azure Container Instances) runs Claude-generated code server-side and returns results/charts/files to the employee.

What it handles: Data analysis on uploaded CSV, running geotechnical calculations, generating charts from borehole data.

Complex — evaluate in Phase 3 — security review required

🔧
Relevance to SRK's existing work

SRK's Data Services team is already using Python for borehole log conversion (Excel → dotPLOT). The chatbot's coding skill can directly support this workflow — employees describe what they need, Claude writes the script, the team reviews and runs it. The existing library management system (Flask/Azure) uses the same tech stack as the chatbot, meaning there is existing in-house expertise to maintain and extend it.

Exit Strategy & Scalability
How SRK avoids being locked in and stays ahead of the game
🔓
The MCP open standard is SRK's insurance policy

The entire skills layer (SharePoint search, project lookup, library integration) is built on the Model Context Protocol — an open, vendor-neutral standard. If SRK ever needs to switch from Claude to another model (GPT-5, Gemini, open-source, or self-hosted), the skills layer does not need to be rewritten. Only the API call in the application layer changes. This is SRK's escape route — and it should be built in from day one.
